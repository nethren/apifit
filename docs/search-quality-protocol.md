# Search quality pilot — frozen before baseline

Date: 2026-09-15. Dataset: `tests/search-quality-cases.json`, version `search-quality-v1-2026-09-15`.

Post-run notice: this v1 holdout is now consumed. See the [results and d19 reference erratum](search-quality-results-2026-09-15.md) before reuse. The frozen case file was preserved for reproducibility, not endorsed as a fresh future test set.

## What this tests

The real `/api/discover` route: natural-language query → internal query expansion → 24 directory candidates → metadata-grounded AI ordering. No user confirmation step, no UI changes, no API execution, no summaries or build briefs generated by this benchmark. Keep the existing US$5 cumulative ledger. Public synthetic cases only; never write real user briefs to benchmark files.

30 cases: 20 development, 10 held out from failure inspection until the implementation is frozen. Coffee and weather are explicitly known regression cases, not novel evidence. This is an author-created, model-assisted pilot, not independent human validation or a statistically representative accuracy study. Do not claim production readiness from these scores.

## Fixed evidence and scoring

Use the same hashed public directory snapshot for both runs: preferred API versions and only the first three MCP pages. Retain source dates and coverage. Missing URLs in replay fail closed; never silently fetch new pages. Missing reference products are source-coverage gaps, not ranking failures. A reference product is a possible core-component lead, not proof of all requested features, present-day access or operational reliability.

Reference products are non-exhaustive. Product identifiers match exactly; do not award credit to arbitrary products from the same provider. A returned item not in the reference or explicit exclusion lists is **unjudged**, not necessarily wrong. Do not modify reference lists based on observed outputs. Further useful alternatives can be noted separately in the review.

Report separately by split:

1. Reference present in loaded source / cases with a reference.
2. Reference in first 24 candidates / source-covered cases.
3. At least one reference in top 3 / all reference cases, and / source-covered cases.
4. Mean reciprocal rank of first reference among returned results, using all reference cases.
5. Explicitly excluded results in top 3; unjudged top-3 results separately. These are not a precision score.
6. Empty-result success for the two unrelated requests. An empty result on a capability query does NOT prove no API exists.
7. HTTP/schema/quote-validation failures; exact quotes do not establish semantic support.
8. Product-duplicate count in top 3 (especially MCP versions).
9. Per-case total latency (p50/p95), actual input/output tokens and settled cost; ambiguous calls retain their reservation. No automatic paid retries.

Provisional target, fixed before baseline: a reference in top 3 for at least 80% of source-covered capability cases; no explicitly excluded top-3 product; both unrelated cases empty; no severe unsupported capability claim in the reviewed sample. This is a development target, not a release certification. Report denominators, missed targets and improvements without concealing regressions. Short samples have high uncertainty.

## Claim review rubric

After baseline, inspect development outputs only. After tuning is frozen, inspect holdout outputs once. For a selected sample, compare each reason/gap to its supplied metadata quote and broader excerpt: supported core action; appropriately qualified partial lead; overstatement; or insufficient evidence. Mark a severe error when an unsupported action/dataset, contradictory geography or invented operational reliability would materially mislead selection. Preserve audit examples and reviewer identity (Codex, not a human evaluator).

## Reference basis and limits

Most references are grounded in public directory descriptions. Named sparse descriptions (Stripe, Twilio and GitHub) intentionally test evidence/retrieval limits: official capability exists, but metadata alone may not justify a claim. Official cross-checks include [Weatherbit](https://www.weatherbit.io/api/weather-forecast-hourly), [Twilio messaging](https://www.twilio.com/docs/messaging/api/message-resource), [Stripe payments](https://docs.stripe.com/api/payment_intents), [TomTom POI search](https://docs.tomtom.com/search-api/documentation/search-service/fuzzy-search), [GitHub issues](https://docs.github.com/en/rest/issues/issues), [Google Books ISBN search](https://developers.google.com/books/docs/v1/using), [Cloud Translation](https://docs.cloud.google.com/translate/docs/reference/rest), [Sheets](https://developers.google.com/workspace/sheets/api/reference/rest), and [Drive uploads](https://developers.google.com/workspace/drive/api/guides/manage-uploads). These pages are not injected into runtime search. Neither provider availability nor pricing is comprehensively audited.

## Run discipline

The runner fingerprints the dataset, snapshot, prompts and implementation before making calls. It writes a manifest and one exclusive result file per case. A rerun cannot overwrite an existing run. Holdout case output stays out of console summaries until explicitly reported. Baseline runs before retrieval changes; after-run uses identical cases/snapshot. Any dataset update starts a new version. Holdout failures may inform the next iteration only with a new holdout set.

No paid search service, deployment, Postman integration or provider-specific hardcoded relevance boost in this iteration. If source coverage needs a new service, document the decision rather than silently adding one.
